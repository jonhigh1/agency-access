AuthHub vs AgencyAccess API v2 — Competitive Report

AgencyAccess shipped a major v2 API + embedded expansion (Oct 2026): scoped API keys, clients/requests CRUD with external IDs, service catalog, signed webhooks (12 event types), iframe embedding with browser events, idempotency keys, usage endpoint, OpenAPI 3.1 spec. This report compares it against AuthHub's current API surface (verified in-repo, Oct 2026) and lays out where we win, where we bleed, and how to beat them.

Them: api.agencyaccess.co/api/v2 + public OpenAPI Us: Fastify REST + MCP agent plane (no public keys) Evidence: their /docs/api reference + our routes audit

Genuine leads. Their announcement courts "AI agent" users, but they ship REST-only. We have the agent-native plane.

Verdict: they built the better classic REST API; we own the agentic layer and the full lifecycle. That is the moat to press.

③ Where we can kick their ass

Don't just close gaps — pair each parity move with a leapfrog they can't copy without rebuilding.

Strategy in one line: match their REST fundamentals in one release, then outflank on agentic + embedded + lifecycle while their v2 is still new.
P0 · Parity bundleShip "Keys + IDs + Idempotency" as one release. Scoped agency API keys with GET /me; immutable external IDs on clients (and requests filterable by them); Idempotency-Key on all creates with replay semantics. This single bundle neutralizes gaps 1–3 and unblocks every CRM integration story they currently win.
P0 · LeapfrogBrand the MCP + approval plane as "the agent-native onboarding API." They market to AI-agent users with REST docs; we already execute through agents with human approval, audit, and risk classes. Publish agent guides + a reference agent integration. Make evaluators compare "their docs for agents" vs "our API for agents" — a fight they lose by architecture.
P1 · LeapfrogEmbed v2 that skips their iframe generation. Match embedUrl + postMessage events + origin allowlist (gap 4), but ship a headless JS SDK on top: framework components, optimistic progress state, and stateVersion-style ordering built in. Their guide warns "browser events can be tampered with — confirm server-side"; an SDK that pairs client events with webhook truth out of the box is the better story.
P1 · LeapfrogTurn diagnostics into the moat: attempt-level + health webhooks. They expose connection.attempt_completed with per-service errors — good. Answer with our token-health edge: proactive connection.degraded / connection.recovered / token.refresh_failed events plus health state in every payload. Nobody else tells the agency before the client fails — sell "onboarding that monitors itself."
P2 · LeapfrogOwn the full lifecycle: access → health → offboarding. Their story ends at request.completed. Ours runs request → connection monitoring → revocation with attestation. Package it as "client access lifecycle API" with catalog (gap 5), granular webhooks (gap 6), OpenAPI + versioning policy (gaps 7–9) included in the same launch. One release that both closes the REST gap and redefines the category around lifecycle.
